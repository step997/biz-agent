# BizAgent 技术栈清单

> 一句话：**Python 3.12 + FastAPI + LangGraph + 自研混合检索 + 原生前端 + SQLite**，全部可离线跑，不依赖任何付费 SaaS（LLM 可选）。
> 选型原则：能装一个包解决的绝不装两个；能在 200 行写清楚的绝不引框架；每个依赖都要能回答"为什么是它"。

## 3. 检索技术细节（三档后端，同一套接口）

`RAG_BACKEND=auto|tfidf|embedding|hybrid`，`auto` = 装得起语义依赖就走 `hybrid`，否则 `tfidf`。

| 环节 | 实现 |
|---|---|
| 分词 | 中文 bigram + 单字 + 英文词（`tokenize()`），无第三方分词器 |
| 词法通道 | BM25（`k1=1.5, b=0.75`），预计算 tf / df / avgdl / idf / 文档长度 |
| 语义通道 | `bge-small-zh-v1.5`（sentence-transformers，CPU，512 维）+ FAISS `IndexFlatIP` 内积检索；query 侧加 bge 官方指令前缀 |
| 语义兜底 | 装了没有 faiss 就用 numpy 点积；装了没有模型就整条降级回 `tfidf` |
| 融合 | RRF（`k=60`，向量序权重 1.2）；`embedding` 档位只看向量序 |
| 置信 | 两档阈值 **按后端各一套**（见下表）+ 结构化门 + 域外门 + 领域门 |
| 缓存 | 索引单例 + `lru_cache(256)` 问句级缓存；chunk 向量落 `data/emb.npy`（68 KB）+ 指纹校验 |
| 预热 | 服务启动的背景线程加载模型建索引（约 9s），不阻塞第一个用户请求 |
| 评测 | `scripts/eval_rag.py --compare --sweep`：13 原始 + 6 同义改写 + 5 负样本 |

**阈值为什么必须分后端**（这是这轮最重要的一条工程结论）：

| 后端 | STRONG | WEAK | 正样本相似度实测区间 |
|---|---|---|---|
| `tfidf` | 0.42 | 0.20 | 0.19 – 0.48（余弦天然偏低） |
| `embedding` | 0.62 | 0.45 | 0.57 – 0.76 |
| `hybrid` | 0.58 | 0.40 | 0.57 – 0.76 |

用同一组阈值必然一边太松一边太紧：把 `tfidf` 的 0.42 套到 bge 上，所有正样本都判 high（无法区分强弱）；把 bge 的 0.62 套到 TF-IDF 上，一条都答不出来。

**三条门控**（都是实测逼出来的，不是拍脑袋）：

| 门 | 规则 | 触发原因（实测） |
|---|---|---|
| 结构化门 | `SO\d{4,}` / `TK…` / `AP…` / "订单号/几单" → low | "SO10204 物流到哪了" 语义分 0.489，与发货制度很近 |
| 域外门 | 天气/股票/汇率/写诗/作文… → low | "今天杭州天气怎么样" 0.507 vs "寄到我这儿大概要几天" 0.529，只差 0.02 |
| 领域门 | 词法后端看字面业务词表；语义后端看"字面词 OR 相似度达标" | 改写句一个业务词都没有，字面门会误杀 |

**为什么默认 hybrid 而不是纯向量**：BM25 在型号/单号/专有名词这类精确匹配上更稳（`10000mAh`、`SF1640…`），向量在口语化改写上更强，RRF 融合两者都兜得住。当前 34 chunk 语料下 hybrid 与 embedding 数字接近 —— 语料小，BM25 只在少数 query 上改变排序；语料涨到几千 chunk 后词法通道的价值才真正显现。

**三档实测对比**（34 chunk / 8 篇制度，`python scripts/eval_rag.py --compare`）：

| 后端 | 样本集 | Top-1 | Top-3 | 负样本拒答 | 正样本相似度 | ms/query |
|---|---|---|---|---|---|---|
| `tfidf` | 原始 13 条 | 92% | 100% | 100% | 0.19–0.48 | 0.2 |
| `tfidf` | 同义改写 6 条 | 83% | 100% | 100% | 0.10–0.25 | 0.2 |
| `embedding` | 原始 13 条 | **100%** | 100% | 100% | 0.57–0.76 | 8.6 |
| `embedding` | 同义改写 6 条 | **100%** | 100% | 100% | 0.49–0.66 | 6.7 |
| `hybrid` | 原始 13 条 | **100%** | 100% | 100% | 0.57–0.76 | 6.4 |
| `hybrid` | 同义改写 6 条 | **100%** | 100% | 100% | 0.49–0.66 | 6.0 |

改写集才是这轮的收益所在：`寄到我这儿大概要几天`、`老客户有优惠吗`、`钱多久能退回我卡上` 与制度原文几乎无字面重合，词法 Top-1 掉到 83%、相似度 0.10–0.25（贴着拒答线），语义后端全中。真实用户本来就不会用文档里的术语提问。

## 4. 性能基线（本机实测，`scripts/bench.py`）

| 路径 | p50 | p95 |
|---|---|---|
| `GET /orders`（业务系统直连） | 30.8 ms | 44.4 ms |
| `query_orders` 工具（含 Pydantic 校验 + 审计） | 31.0 ms | 55.4 ms |
| RAG 词法（`tfidf`，单次检索） | 0.2 ms | — |
| RAG 语义（`hybrid`，含 bge 编码 + FAISS 检索） | 6.4 ms | — |
| RAG 问句缓存命中 | 0.01 ms | 0.01 ms |
| RAG 冷启动（加载 bge + 建向量，启动时后台做一次） | 9.3 s | — |
| 整条图单轮，offline 规则规划 | 42 ms | 60 ms |
| 整条图单轮，DeepSeek | 1.4 – 5.3 s | — |
| SSE 首字（`/chat/stream`，首条 `delta` 到达） | 3.1 – 4.2 s | — |
| SSE 首字（拦截路径，guard 直接跳 compose） | 52 ms | — |
| SSE 首条事件（`guard`，纯代码判定） | ~20 ms | — |

结论：**业务与工具层不是瓶颈，模型调用是**。所以工程重点放在"减少无谓的模型调用"（工具去重、guard 前置拦截、离线规划器兜底、问句缓存），而不是微优化 SQL。语义检索 6.4ms 相比模型 1.4–5.3s 完全可以忽略，但 9.3s 的模型冷启动必须挪到启动期后台线程，否则第一个用户要等。

## 5. 这一轮做的优化

| 优化 | 位置 | 效果 |
|---|---|---|
| SQLite 开 WAL + busy_timeout + 外键约束 | `biz_system/db.py` `connect()` | 读写不互相锁；演示时前端轮询不再卡写操作 |
| 补 5 个索引（`orders.customer_id` / `tickets.order_id` / `customers.name` / `inventory.product_id` / `approvals.status`） | 同上 `SCHEMA` | 按客户名查单、超时工单、待审批列表走索引 |
| 工具对象与 schema 只构造一次 | `tools/biz_tools.py` `build_registry` | 每次 `/chat` 省掉 9 个 Tool + Pydantic schema 重建 |
| 出网统一到一个 `_request()`，连接级失败重试 1 次（4xx/5xx 不重试） | 同上 | 业务系统抖动不再直接变成"工具失败" |
| 审计库加锁 + WAL + 两个复合索引 | `agent/audit.py` | 线程池并发写不再争用同一连接 |
| RAG 问句级 `lru_cache(256)` | `rag/index.py` | 重复提问 24.9ms → 0.02ms |
| 写操作代码级护栏（`planner.guard_plan`） | `agent/planner.py`、`agent/graph.py` `node_plan` | 制度类问题即便模型想建审批单也被剔除，并回落 `query_policy`；写意图靠动作词（提交/申请/发起/建个/帮我建）判定，不靠 prompt 自觉 |
| 检索升级为可切三档（词法/语义/混合），bge-small-zh + FAISS | `rag/embedder.py`、`rag/index.py` | 同义改写 Top-1 83% → 100%；装不上自动降级，不引硬依赖 |
| 阈值按后端分套（0.42/0.20、0.62/0.45、0.58/0.40） | 同上 `THRESHOLDS` | 一套阈值不可能同时适配 TF-IDF 余弦与 bge 向量 |
| 三条门控：结构化 / 域外词 / 领域门分后端 | 同上 | 负样本拒答从 80% 回到 100%（"杭州天气"0.507 与"寄到我这儿"0.529 只差 0.02） |
| 向量落盘 + 指纹缓存 + 启动后台预热 | `rag/embedder.py`、`agent/main.py` `lifespan` | 冷启动 9.3s 挪到启动期；改制度文档自动重建 |
| Guard 拦截直接进 compose | `agent/graph.py` `_route_after_guard` | 拦截路径从"还要跑一次模型"变成 15ms 返回 |
| 同一轮同工具只执行一次 | `agent/graph.py` `node_plan`/`node_tools` | 去掉模型重复规划带来的 2–3 倍无效调用 |
| `/metrics` 暴露工具调用/失败/耗时/拦截数 | `agent/main.py` | 不引组件即可被 Prometheus 抓取 |
| 结构化日志（每轮一条：thread/mode/tools/conf/耗时） | 同上 | 出问题先看日志一条线 |
| 前端：发送中状态、Esc 清空、820px 移动端布局、审计表参数列 | `web/index.html` | 手机上也能演示，参数列不再空 |
| **SSE 流式**：`stream_bus` 事件总线 + `graph.invoke` 后台线程 + 节点内 `emit` | `agent/stream_bus.py`、`agent/graph.py`、`agent/main.py` `chat_stream` | 首字从"3.5s 白屏"变成 3.0–3.7s 起逐字出；`guard` 事件 ~20ms 就能让轨迹面板动起来。**踩过的坑**：LangGraph 同步图 + `stream_mode="messages"` 拿不到真 token（只在 super-step 边界 yield，首字 8.8s 比不流式还慢）；async `astream` 与 `SqliteSaver` 不兼容（要换 `AsyncSqliteSaver`） |
| 会话列表 + 历史回放 | `agent/main.py` `GET /threads`、`web/index.html` | 演示可以"接着上一轮问"，多轮指代有据可查 |

## 7. 从 Demo 到生产的替换清单

| 现在 | 生产建议 | 要改的地方 |
|---|---|---|
| SQLite | PostgreSQL / 客户现有 ERP 库 | `biz_system/db.py` 连接层；工具层不动 |
| 自研 BM25+TFIDF（默认，靠 bge 兜语义） | 更大向量模型（bge-large / gte-Qwen）+ Milvus/Qdrant + rerank（bge-reranker） | `rag/embedder.py` 换 `EMB_MODEL`，`rag/index.py` 的 `_build_faiss()` 换成远端向量库客户端；`search()` 签名不变 |
| 词法 0.2ms / 语义 6.4ms（CPU） | 语义通道上 GPU 或 ONNX Runtime 量化 | `rag/embedder.py` 的 device / backend 参数 |
| `lru_cache` 问句缓存 | Redis | `rag/index.py` 缓存层 |
| SqliteSaver | Redis/Postgres checkpointer | `agent/graph.py` `get_graph()` |
| 单进程 uvicorn | gunicorn + 多 worker + Nginx | 部署脚本；注意审计库改连接池 |
| `/metrics` 文本 | Prometheus + Grafana + 告警 | 直接抓 `/metrics`，无需改代码 |
| 企业微信 Webhook | 客户 IM（钉钉/飞书/企微应用） | `agent/jobs.py` `push()` |
| `demo-key` | 每租户独立 Key + 角色权限（客服/仓管/财务可见工具不同） | `tools/base.py` 增加 `roles` 字段 + 网关校验 |
| 无向量化成本控制 | token 计费与配额（`llm_usage` 表） | `agent/llm.py` 包一层用量计量 |
